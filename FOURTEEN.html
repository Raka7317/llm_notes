Why Do We Need Multiple Evaluation Pipelines?

A single LLM-based application can have multiple failure points and multiple risk categories. Therefore, a production-grade application usually needs multiple evaluation pipelines at the component, workflow, and entire-application levels.

2. The Key Statement: One Application Can Have Several LLM Evals

The previous session ended with an important statement: generally speaking, one LLM-based application can have several LLM evals.

This is the starting point of today's session. The key question is: Why do we need multiple evaluation pipelines? Why can't we evaluate the entire application using only one evaluation pipeline?

3. Reason #1 — Multiple Failure Points

An LLM-based application can fail at several different points. A single application is not necessarily one indivisible component. It is usually made up of multiple components that interact with each other.

Core idea: Multiple failure points → multiple places to evaluate.

Example: A RAG Chatbot

Suppose we are building a RAG chatbot for our company, school, or college.

User Query
→
Retriever
→
Vector Database
→
Retrieved Context
→
Generator / LLM
→
Final Answer

The rough RAG flow is:

  1. A query arrives at the retriever.
  2. The retriever searches the vector database.
  3. Relevant documents are retrieved.
  4. The query and retrieved documents are passed to the generator.
  5. The generator, which is an LLM, generates an answer using the retrieved context.

4. RAG Has Multiple Failure Points

Failure Point #1 — Retriever

The retriever might fetch the wrong documents. If the wrong documents are retrieved, the generator may produce a wrong answer because it is working from incorrect context.

Failure Point #2 — Generator

The retriever might work correctly, but the generator could ignore the relevant context and hallucinate or generate an incorrect answer.

RETRIEVER EVAL

Are We Retrieving the Right Documents?

The evaluation pipeline checks whether a given query retrieves the relevant documents from the vector database.

GENERATOR EVAL

Is the Answer Faithful?

The evaluation pipeline checks whether the generated answer is grounded in the retrieved context.

5. Retriever Evaluation

The goal of the retriever is simple: given a query, retrieve relevant documents. Therefore, the retriever evaluation pipeline should check:

Given a query, are we getting the right relevant documents?

For example, if a user asks: “What is the duration of the Machine Learning course?” and one of the retrieved documents clearly states that the course duration is eight weeks, the retriever has successfully retrieved a document containing the required information.

6. Generator Evaluation — Faithfulness / Groundedness

The generator receives the query and retrieved context and generates the final answer. The evaluation should check whether the answer is faithful to the supplied context.

Faithfulness / Groundedness: The generated answer should be supported by the retrieved context and should not invent additional facts.

Example:

Question: “What is the duration of the Machine Learning course?”

Retrieved document: “The duration of the Machine Learning course is 3 weeks.”

Good answer: “The Machine Learning course duration is 3 weeks.”

The answer should not randomly add unrelated information such as: “It's a great course,” “You can also purchase the Python course,” or “The Python course duration is four weeks.”

7. Why Component-Level Evals Are Not Enough

Now assume that both evaluation pipelines tell us that the retriever and generator are individually working correctly. Does that guarantee that the complete RAG application will work correctly? No.

The RAG Failure Scenario

Suppose the user asks: “What is the duration of the Machine Learning course?”

The retriever has K = 5.

That means it retrieves the five most relevant documents. Suppose the retrieved documents are:

RankDocumentContent
D1Random informationUnrelated information.
D2Random informationUnrelated information.
D3Random informationUnrelated information.
D4Random informationUnrelated information.
D5Relevant document“The duration of the ML course is 8 weeks.”
Did the retriever do its job? Yes. The relevant answer was found within the top K = 5 retrieved documents.

Now all five documents are passed to the generator along with the user query. Suppose the system prompt instructs the generator to give higher priority to the higher-ranked documents. The generator may focus more on D1, D2, D3 and D4.

Imagine that one of the higher-ranked documents says: “The duration of the Python course is 6 weeks.” The generator might incorrectly combine the information and answer: “The duration of the ML course is 6 weeks.”

The final answer is wrong. However, the generator may still have followed its instructions correctly. The problem came from the interaction between retrieval ranking and generation.

8. Workflow-Level Evaluation

This example demonstrates why we need not only individual component-level evaluations, but also a workflow-level evaluation.

The retriever can work independently. The generator can work independently. Yet the combination of both can still fail.

Retriever Eval
+
Generator Eval
+
Workflow Eval
→
Better RAG Reliability

A workflow-level eval would detect that the final answer is wrong and could help identify the underlying issue: the correct document exists, but it is too low in the priority order.

Possible Fix: Reranker

A reranker can reorder the retrieved documents after retrieval. If D5 is actually the most relevant document, the reranker can move D5 to the top:

D5 — Most Relevant
→
D1
→
D2
→
D3
→
D4

This can improve the complete RAG workflow because the generator now receives the most relevant information with the highest priority.

9. Even Workflow-Level Evaluation Is Not Enough

Suppose now that:

  • The retriever is working correctly.
  • The generator is working correctly.
  • The retriever + generator workflow is working correctly.

Does this guarantee that the RAG application is production-ready? Still no.

Example: Latency

Suppose the entire pipeline takes 10 seconds to answer one question. The answer may be correct, but the user has to wait ten seconds.

Production question: Is the application good enough to ship if every answer takes 10 seconds?

Answer: No. We need an application-level evaluation for latency.

10. Three Levels Where Failure Can Occur

LevelWhat Can Fail?Examples
Component Level Individual components can fail. System prompt, retriever, reranker, query rewriter, embedding model, vector database, output parser, tool selector, memory, guardrails.
Workflow Level The interaction between components can fail even when components work individually. RAG workflow, agent workflow, multi-turn chatbot workflow.
Entire Application Level The complete product can fail to satisfy production requirements. Latency, cost, time-to-first-token, reliability, overall user experience.
Key takeaway: Individual components can work correctly while the complete workflow still fails. And the workflow can work correctly while the complete application still fails operationally.

11. Reason #2 — Multiple Risk Categories

There is another major reason why an LLM application needs multiple evaluation pipelines: multiple risk categories.

We have three broad levels where evaluations can be placed:

  1. Individual components
  2. Workflows
  3. Entire application

But each of these levels can have multiple aspects that need to be evaluated. For example, a RAG chatbot's answer should not only be correct and helpful; it should also be safe.

12. Three Broad Risk Categories

01

Application Quality

Does the application actually perform its intended job well? Does it provide correct, relevant, and complete answers?

02

Safety

Is the output safe? Does the system avoid toxic, harmful, biased, private, or otherwise unsafe behavior?

03

Operations

Can the application run fast, cheaply, reliably, and efficiently after deployment?

13. Application Quality

Application quality tells us whether the system is doing its actual job well. The answer should be correct, relevant, complete, and appropriate for the user's request.

General LLM Application

Risk CategoryWhat It Checks
Correctness / AccuracyIs the generated answer accurate and correct?
RelevanceIs the answer related to what the user asked?
CompletenessDid the system answer all required parts of the request?
Instruction FollowingDid the model follow the requested format, length, style, or other constraints?

For example, in a text summarizer, you would evaluate whether the summary is accurate, relevant, complete, and follows the requested format or length.

14. RAG-Specific Risk Categories

Risk CategoryMeaning
Context RelevanceAre the retrieved documents relevant to the user's query?
Retriever RecallDid the retriever successfully retrieve the required relevant information?
Groundedness / FaithfulnessIs the generated answer supported by the retrieved context?
Citation AccuracyDo citations correctly identify the documents supporting the generated claims?

15. Agent-Specific Risk Categories

Risk CategoryMeaning

Parameter CorrectnessDoes the agent provide the correct parameters when calling a tool?

Error RecoveryCan the agent recover when something goes wrong during task execution?

16. Multi-Turn Chatbot Risk Categories

Risk CategoryMeaning
Context RetentionHow well does the chatbot remember and use relevant previous conversation?
Clarification BehaviorWhen the user's request is ambiguous or unclear, does the chatbot ask an appropriate clarification question?

17. Safety Risk Categories

Safety evaluation has several important dimensions:

RiskWhat We Check
ToxicityDoes the system produce toxic or abusive content?
Harmful ContentDoes the system produce harmful content such as inappropriate self-harm, weapons, or illegal-activity-related content?
BiasDoes the system behave unfairly or differently based on user characteristics or profiles?
Privacy / PII LeakageDoes the chatbot reveal personal or private information, such as another person's contact details or sensitive data?
Prompt Injection / Jailbreak ResistanceCan a user manipulate the system into performing actions or generating content that it should not?

18. Operational Risk Categories

After deployment, the application also needs to be evaluated for operational performance.

Risk CategoryWhat It Checks
LatencyHow quickly does the application respond?
Cost per RequestHow much does each request cost?
Token EfficiencyHow efficiently are input and output tokens being used?
Error / Failure RateHow frequently does the system fail?
Latency Under LoadDoes the application remain responsive when traffic increases?
Time to First TokenHow long does the user wait before the first generated token appears?

For example, the same application can have:

  • One evaluation pipeline for safety.
  • One evaluation pipeline for correctness.

  • One evaluation pipeline for groundedness.
  • One evaluation pipeline for cost.
  • Additional component- or workflow-specific evaluations.

20. Final Summary

The entire discussion can be summarized in one central idea: LLM-based applications usually need multiple evaluation pipelines.

Reason #1 — Multiple Failure Points

An application can fail at the component level, workflow level, or entire application level. Therefore, we need evaluations at each relevant level.

Reason #2 — Multiple Risk Categories

Even at the same level, there can be multiple things to evaluate: quality, safety, and operational performance. Therefore, one metric or one evaluation pipeline is rarely enough.

Why Multiple Evals?Explanation
Multiple Failure PointsComponents can fail individually, components can fail in combination, and the complete application can fail operationally.
Multiple Risk CategoriesThe system must be correct and useful, safe for users, and operationally fast, cheap, and reliable.
Core takeaway:
A production-grade LLM application is not just an LLM. It is a collection of components and workflows. Because there are multiple failure points and multiple risk categories, we need multiple evaluation pipelines to understand whether the system is actually ready for real users.
