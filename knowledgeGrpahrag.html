How Knowledge Graph RAG Stores & Retrieves Data

A practical, step-by-step guide showing how documents become entities and relationships, where the graph is stored, how retrieval happens, which tools are used, and how the retrieved graph facts finally reach the LLM.

01 • START HERE

The Big Picture

The easiest way to understand Knowledge Graph RAG is to separate it into two jobs:

Job 1 — Create the graph

Convert unstructured documents into:

Entities + Relationships + Properties

Job 2 — Retrieve from the graph

Find relevant entities and follow their relationships using graph queries or traversal.

Documents
→
Entity Extraction
→
Relationship Extraction
→
Knowledge Graph
→
Graph Query
→
LLM
Core idea: A Knowledge Graph does not primarily retrieve by embedding similarity. It stores explicit connections such as Rakesh —WORKS_AT→ Google and retrieves information by querying or traversing those connections.
02 • GRAPH CREATION

Step 1 — Start with a Document

Suppose your company has this text:

"Rakesh works at Google as an AI Engineer.
Google is headquartered in California.
Sundar Pichai is the CEO of Google."

Extract the entities

Rakesh          → PERSON
Google          → ORGANIZATION
AI Engineer     → JOB_TITLE
California      → LOCATION
Sundar Pichai   → PERSON

Extract the relationships

Rakesh         → WORKS_AT          → Google
Rakesh         → JOB_TITLE         → AI Engineer
Google         → HEADQUARTERED_IN  → California
Sundar Pichai  → CEO_OF            → Google
These Subject → Relationship → Object statements are commonly called triples.

Important: A Knowledge Graph is a logical data model. The physical storage depends on the graph technology you choose. One common choice is a property-graph database such as Neo4j. Another family is RDF triple stores queried with SPARQL.
04 • GRAPH DATABASE

Using Neo4j to Store the Graph

For learning and implementing Graph RAG, Neo4j + Cypher is a practical stack. Neo4j stores nodes, relationships, and properties in a property-graph model.

Create nodes

CREATE (r:Person {name: "Rakesh"})
CREATE (g:Company {name: "Google"})
CREATE (c:Location {name: "California"})

Create relationships

MATCH (r:Person {name: "Rakesh"}),
      (g:Company {name: "Google"})
CREATE (r)-[:WORKS_AT]->(g)

Create the complete example

CREATE (r:Person {name: "Rakesh"})
CREATE (g:Company {name: "Google"})
CREATE (c:Location {name: "California"})
CREATE (s:Person {name: "Sundar Pichai"})

CREATE (r)-[:WORKS_AT {role:"AI Engineer"}]->(g)
CREATE (g)-[:HEADQUARTERED_IN]->(c)
CREATE (s)-[:CEO_OF]->(g)

The stored graph becomes

Rakesh ── WORKS_AT ──▶ Google ── HEADQUARTERED_IN ──▶ California
Sundar Pichai ── CEO_OF ──▶ Google
05 • RETRIEVAL

How Does Searching Take Place?

Suppose the user asks:

"Where is the company Rakesh works for headquartered?"

The system needs to find this path:

Rakesh ── WORKS_AT ──▶ Company ── HEADQUARTERED_IN ──▶ Location

Graph traversal

Start at the entity Rakesh.

Rakesh
  │
  ├── WORKS_AT ──> Google
  │
  └── JOB_TITLE ──> AI Engineer

The question requires WORKS_AT, so follow that edge:

Rakesh
   │
   └── WORKS_AT
          ↓
        Google

Now we need HEADQUARTERED_IN:

Google
   │
   ├── HEADQUARTERED_IN ──> California
   │
   └── CEO_OF ──> Sundar Pichai

Final retrieved fact:

Google → HEADQUARTERED_IN → California

This process of following relationships is called graph traversal.

06 • SEARCH LANGUAGE

Using Cypher to Search Neo4j

Cypher is the query language used with Neo4j. Instead of doing vector similarity search, you describe the graph pattern you want to find.

Simple query

MATCH (p:Person {name: "Rakesh"})
      -[:WORKS_AT]->
      (c:Company)
RETURN c.name

Result:

Google

Two-hop query

Now find where Rakesh's company is headquartered:

MATCH (p:Person {name: "Rakesh"})
      -[:WORKS_AT]->
      (c:Company)
      -[:HEADQUARTERED_IN]->
      (l:Location)
RETURN c.name, l.name

Result:

Company      Location
-------------------------
Google       California
Important: The database is not asking "which text is semantically similar?" It is matching a graph pattern.

09 • VECTORLESS RAG

Why Is This Called Vectorless RAG?

Traditional vector RAG normally uses embeddings and a vector database:

Document
   ↓
Chunk
   ↓
Embedding Model
   ↓
Vector
   ↓
Vector Database
   ↓
Similarity Search
   ↓
Relevant Chunks

Knowledge Graph RAG can retrieve without embeddings:

Document
   ↓
Entity Extraction
   ↓
Relationship Extraction
   ↓
Knowledge Graph
   ↓
Cypher / Graph Traversal
   ↓
Relevant Facts

Three retrieval methods

MethodQuestion it answersTypical Tool
BM25 Which text contains important matching terms? Elasticsearch / Lucene / OpenSearch
Vector Search Which text has similar semantic meaning? FAISS / Qdrant / Pinecone etc.
Knowledge Graph Which entities are connected, and how? Neo4j + Cypher
Vectorless does not mean "no retrieval." It means you can perform retrieval using non-vector methods such as BM25, graph traversal, SQL, metadata filtering, or combinations of them.

12 • FINAL CHEAT SHEET

Remember This

1. What is stored?
Entities are stored as nodes. Relationships are stored as edges. Additional attributes can be stored as properties.
2. What is the basic fact format?
(Subject, Predicate, Object)
Example: (Rakesh, WORKS_AT, Google)
3. Where can it be stored?
A property graph can be stored in Neo4j. RDF knowledge can be stored in an RDF triple store.
4. How do you search Neo4j?
Use Cypher to match graph patterns and traverse relationships.
5. How does Graph RAG work?
Question → query understanding → Cypher/graph retrieval → graph facts → LLM → answer.
6. Why vectorless?
Because graph retrieval can work without embeddings or vector similarity search.

Best learning path for AI Engineering:
Start with Neo4j → Cypher → create nodes/relationships → graph traversal → LLM-to-Cypher → Graph RAG. Then learn how to combine the graph with BM25 and vector retrieval for hybrid RAG.
